# 管理系統帳號申請與生命週期標準

## 1. 目的與適用範圍

本文件定義內部資料管理系統共用的帳號申請、審核、登入、停權、刪除及密碼重設流程。新系統原則上應直接採用；既有系統調整時，除非有明確業務需求，亦應依本標準實作。

本標準的主要原則如下：

- 帳號採人工審核，不使用 Email 驗證信。
- 不提供公開的「忘記密碼」功能，也不透過 Email 重設密碼。
- 忘記密碼時，由管理員確認本人身分後產生一次性顯示的臨時密碼。
- 使用臨時密碼登入後，必須先設定新密碼，才能使用其他功能。
- 停權與刪除是不同操作；停權可恢復，刪除預設採軟刪除以保留資料關聯。
- 所有帳號管理操作須受權限控制並留下稽核紀錄，但紀錄不得包含任何明文密碼。

## 2. 角色與責任

### 2.1 申請者／一般使用者

- 透過公開申請頁提交姓名、Email、單位、職稱及密碼。
- 申請後等待管理員審核，不會自動登入。
- 忘記密碼時，依登入頁提示聯絡管理員。
- 收到臨時密碼後，須於期限內登入並立即設定新密碼。

### 2.2 帳號管理員

- 查核申請者身分與申請資料。
- 核准或拒絕帳號申請。
- 依業務需要調整角色與權限。
- 確認本人身分後產生臨時密碼，並透過適當的個別管道交付。
- 執行停權、恢復、軟刪除及還原。
- 不得將臨時密碼貼在共用文件、公開群組或系統備註中。

## 3. 帳號狀態模型

`users.status` 應使用明確狀態，不以 Email 驗證欄位代替審核狀態。

| 狀態 | 說明 | 可以登入 | 管理員可執行 |
| --- | --- | --- | --- |
| `pending` | 申請已送出，等待審核 | 否 | 核准、拒絕、刪除 |
| `active` | 已核准且啟用 | 是 | 停權、產生臨時密碼、編輯、刪除 |
| `rejected` | 申請遭拒絕 | 否 | 重新核准、刪除 |
| `suspended` | 已停權 | 否 | 恢復、刪除 |
| 軟刪除 | 已自一般操作清單移除 | 否 | 還原（限授權管理員） |

建議狀態轉換：

```text
pending  ──核准──> active ──停權──> suspended
   │                  ▲                 │
   └──拒絕──> rejected ──重新核准───────┘

pending / active / rejected / suspended ──刪除──> 軟刪除
軟刪除 ──還原──> 刪除前狀態，或由管理員重新指定狀態
```

帳號狀態與角色必須分開保存。`active` 只表示允許登入，不代表擁有管理員權限。

## 4. 註冊與審核流程

### 4.1 送出申請

1. 使用者填寫申請表並自行設定密碼。
2. 系統驗證 Email 唯一性及密碼強度。
3. 建立 `status = pending` 的帳號。
4. 不觸發註冊郵件、不設定 Email 驗證時間，也不自動登入。
5. 導回登入頁或完成頁，顯示：「帳號申請已送出，請等待管理員審核。」

申請人使用待審核帳號登入時，應顯示：「帳號仍在等待管理員審核。」不可只顯示籠統的帳號或密碼錯誤。

### 4.2 管理員核准

管理介面應提供「待審核」分頁。核准時：

- 將 `status` 改為 `active`。
- 寫入 `approved_at` 與 `approved_by`。
- 設定使用者角色及必要的資料範圍權限。
- 寫入稽核紀錄。

核准後不寄通知信。管理員依組織既有聯絡方式通知申請者。

### 4.3 拒絕

- 將 `status` 改為 `rejected`。
- 建議保存管理員可見的拒絕原因 `rejected_reason`。
- 拒絕原因不得包含密碼或不必要的個人敏感資料。

## 5. 登入頁與登入規則

登入表單只提供 Email、密碼、記住我及登入按鈕。在密碼欄位附近顯示純文字：

> 忘記密碼請洽管理員。

不得顯示或保留「忘記密碼」連結及公開密碼重設路由。

登入檢查順序：

1. 套用 IP 與帳號登入節流。
2. 驗證 Email 與密碼。
3. 檢查帳號是否被軟刪除。
4. 檢查 `status`：只有 `active` 可登入。
5. 若使用者須強制改密碼，檢查臨時密碼是否過期。
6. 登入成功後重新產生 Session ID。
7. 若 `must_change_password = true`，導向強制修改密碼頁；否則導向原目標頁或系統首頁。

錯誤訊息至少應區分：

- 帳號或密碼錯誤。
- 帳號仍在等待審核。
- 帳號申請未通過。
- 帳號已停權，請洽管理員。
- 臨時密碼已過期，請洽管理員重新產生。

## 6. 管理員重設密碼

### 6.1 產生臨時密碼

管理員在使用者管理頁按「產生臨時密碼」後，系統必須：

1. 顯示確認對話框，說明舊密碼與既有登入將失效。
2. 使用密碼學安全的亂數產生器產生至少 16 字元的臨時密碼。
3. 只將雜湊值存入 `users.password`。
4. 設定 `must_change_password = true`。
5. 設定 `temporary_password_expires_at`，預設為產生後 24 小時。
6. 清除 `remember_token`，並撤銷該使用者所有既有 Session 或 API token。
7. 寫入不含密碼內容的稽核紀錄。
8. 在成功回應中只顯示一次明文臨時密碼，並加上 `Cache-Control: no-store`。

臨時密碼不得：

- 寫入資料庫欄位、Session、一般應用程式 log 或稽核 log。
- 透過 URL query string 傳遞。
- 在重新整理頁面後再次取得。
- 由管理員自行指定成容易猜測的內容。

若管理員關閉畫面前未保存臨時密碼，應重新產生一組；系統不可嘗試找回舊的明文密碼。

### 6.2 交付臨時密碼

系統不寄信。管理員在確認使用者身分後，透過個別且適當的管道交付。應同時告知：

- 臨時密碼有效期限。
- 第一次登入後必須立即修改。
- 若密碼過期，需再次聯絡管理員。

## 7. 強制修改密碼

`must_change_password = true` 的使用者登入後，只允許存取：

- 強制修改密碼頁及提交動作。
- 登出動作。
- 維持頁面運作所需的靜態資源。

此限制必須由 middleware 或同等的伺服器端機制執行，不可只依靠畫面導向。

修改密碼時：

1. 驗證新密碼及確認欄位。
2. 新密碼須符合系統密碼強度規則。
3. 更新密碼雜湊。
4. 設定 `must_change_password = false`。
5. 清除 `temporary_password_expires_at`。
6. 撤銷其他既有 Session，並重新產生 `remember_token`。
7. 登出目前 Session，導回登入頁並要求使用新密碼登入。
8. 寫入不含密碼內容的稽核紀錄。

一般使用者主動修改密碼時仍須驗證目前密碼；以臨時密碼登入的強制修改頁，可以把目前登入驗證視為臨時密碼已驗證，但必須受期限與專用 middleware 保護。

## 8. 停權、刪除與還原

### 8.1 停權

停權適用於暫時禁止使用，但仍須保留帳號及未來恢復可能性的情況。

- 將 `status` 改為 `suspended`。
- 立即撤銷該使用者所有 Session、API token 與記住我憑證。
- 保留帳號、角色、資料關聯及操作歷史。
- 恢復時改回 `active`，並記錄執行者與時間。

### 8.2 刪除

管理介面的「刪除使用者」預設執行軟刪除：

- 設定 `deleted_at` 與 `deleted_by`。
- 立即撤銷所有 Session、API token 與記住我憑證。
- 使用者不得登入，也不出現在一般帳號清單。
- 保留其建立或修改的業務資料、外鍵關聯及稽核歷史。
- 刪除前必須顯示包含使用者姓名與 Email 的確認訊息。

只有在法規、個資請求或明確資料治理程序要求時，才能永久刪除或匿名化。永久刪除前必須先盤點關聯資料，且不應作為一般管理頁按鈕。

### 8.3 管理員保護

- 使用者不得停權或刪除自己。
- 不得停權、降權或刪除最後一位有效的系統管理員。
- 還原軟刪除帳號後，必須重新檢查其狀態與權限，不得無條件恢復敏感權限。

## 9. 建議資料欄位

`users` 至少應具備：

| 欄位 | 建議型態 | 用途 |
| --- | --- | --- |
| `status` | string(20), indexed | `pending/active/rejected/suspended` |
| `approved_at` | timestamp nullable | 核准時間 |
| `approved_by` | unsigned bigint nullable | 核准管理員 |
| `rejected_reason` | text nullable | 拒絕原因 |
| `must_change_password` | boolean default false | 是否強制修改密碼 |
| `temporary_password_expires_at` | timestamp nullable | 臨時密碼到期時間 |
| `deleted_at` | timestamp nullable | 軟刪除時間 |
| `deleted_by` | unsigned bigint nullable | 刪除管理員 |
| `remember_token` | string nullable | Laravel 記住登入憑證 |

建議另建 `account_audit_logs`，至少保存：

- 執行者 ID。
- 動作名稱。
- 目標使用者 ID。
- 變更前後的非敏感欄位。
- IP、User-Agent 與執行時間。

禁止保存密碼、臨時密碼、Session ID、token 或完整 Cookie。

## 10. 管理介面規格

使用者管理頁建議提供以下分頁：

- 待審核。
- 有效帳號。
- 已停權。
- 已拒絕。
- 已刪除。

依狀態顯示可用動作：

| 目前狀態 | 動作 |
| --- | --- |
| 待審核 | 核准、拒絕、編輯、刪除 |
| 有效 | 編輯、產生臨時密碼、停權、刪除 |
| 已停權 | 恢復、產生臨時密碼、刪除 |
| 已拒絕 | 重新核准、刪除 |
| 已刪除 | 還原 |

產生臨時密碼成功頁必須清楚顯示「只顯示這一次」，並提供複製按鈕，但不得把密碼放進可被前端分析工具或錯誤回報自動收集的資料中。

## 11. 稽核事件名稱

各系統宜統一使用以下事件名稱：

- `account.application_submitted`
- `account.approved`
- `account.rejected`
- `account.suspended`
- `account.reactivated`
- `account.deleted`
- `account.restored`
- `account.temporary_password_created`
- `account.password_changed`
- `account.role_changed`

## 12. 本專案導入規劃

外來植物調查系統目前已具備 Laravel Session、使用者軟刪除與使用者管理頁，可分階段調整：

### 第一階段：資料結構

- 新增 `status`、`approved_at`、`approved_by`、`rejected_reason`、`must_change_password`、`temporary_password_expires_at`。
- 既有未刪除使用者遷移為 `active`，避免部署後全部無法登入。
- 既有管理員填入合理的核准時間；無法辨識核准者時，`approved_by` 可暫時為 `null`。
- 保留既有 `deleted_at`、`deleted_by`。
- `email_verified_at` 不再作為存取條件；確認沒有舊程式依賴後再另案移除欄位。

### 第二階段：申請與登入

- 註冊後建立 `pending` 帳號，不觸發 `Registered` 寄信事件、不自動登入。
- 移除 Email 驗證相關路由、通知及 `verified` middleware。
- 移除忘記密碼與 Email 密碼重設路由和畫面。
- 登入頁將連結改為「忘記密碼請洽管理員」。
- 登入驗證加入帳號狀態及臨時密碼期限檢查。

### 第三階段：管理操作

- 使用者管理加入各狀態分頁、核准、拒絕、停權、恢復、刪除與還原。
- 將目前「寄送密碼重設信」改為「產生臨時密碼」。
- 產生臨時密碼時刪除 `sessions` 表內該使用者的 Session，並清除 `remember_token`。
- 保留目前防止停用自己與最後一位管理員的保護，擴充到刪除及降權操作。

### 第四階段：強制修改與稽核

- 新增強制修改密碼 middleware、頁面與提交動作。
- 所有已登入的業務路由與 Livewire 請求均須套用帳號有效性及強制改密碼檢查。
- 建立帳號管理稽核紀錄。
- 移除不再使用的 Email 驗證通知類別及密碼重設程式。

## 13. 驗收標準

至少應具備下列自動測試或驗收案例：

1. 新申請帳號為 `pending`，不寄信且不自動登入。
2. 待審核、拒絕、停權及軟刪除帳號皆無法登入，訊息符合狀態。
3. 管理員核准後帳號可登入。
4. 登入頁沒有忘記密碼連結，並顯示聯絡管理員提示。
5. 產生臨時密碼後，舊密碼及既有 Session 立即失效。
6. 臨時密碼只在當次成功回應顯示，資料庫與 log 找不到明文。
7. 臨時密碼過期後不可登入。
8. 使用有效臨時密碼登入後，存取任何其他業務頁面都會被導向修改密碼頁。
9. 修改密碼成功後，臨時密碼失效並要求以新密碼重新登入。
10. 停權可恢復；軟刪除帳號可由授權管理員還原。
11. 使用者不能停權或刪除自己，也不能移除最後一位有效管理員。
12. 所有帳號管理操作皆有稽核事件，且不包含密碼或 token。

## 14. 參考實作結論

本標準綜合目前福山（FDP）與 LTSER 的既有做法：

- 採用福山的伺服器端 middleware 強制導向修改密碼頁。
- 採用 LTSER 的明確帳號狀態、24 小時臨時密碼期限、一次性顯示及登入憑證撤銷設計。
- 補上兩者在不同程度上欠缺的統一稽核、軟刪除語意、Session 撤銷及最後管理員保護要求。

後續管理系統若無特殊需求，應使用本文件的欄位名稱、狀態值、稽核事件名稱及驗收案例，以降低跨系統維護成本。
